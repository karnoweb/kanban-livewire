# دستور اجرایی شماره ۱ — تثبیت و توسعه Kanban سازمانی (بدون Task Manager)

**وضعیت:** دستور پیاده‌سازی برای Agent، نه گزارش امکانات پیاده‌سازی‌شده  
**مبنای کد:** `kanban-livewire.zip` ارسال‌شده؛ در زمان اجرا نسخه جاری مخزن مرجع نهایی است.  
**نام فعلی پکیج:** `karnoweb/laravel-livewire-kanban`  
**محیط مشاهده‌شده در ZIP:** PHP ^8.3، Laravel 13، Livewire 4  
**قاعده:** در همین مخزن تغییر بده؛ پکیج جدید، مدل Task یا Migration تجاری اجباری ایجاد نکن.

## ۰. مأموریت و مرز این مرحله

تو مهندس ارشد Laravel/Livewire و معمار پکیج هستی. باید **پکیج Kanban موجود** را به یک رابط سازمانی عمومی برای مدل‌هایی مانند `Task`, `Ticket`, `Order`, `CRM Opportunity` و سایر منابع تبدیل کنی. این مرحله، آماده‌سازی Kanban برای استفاده مستقل و اتصال آینده به Task Manager است؛ **خود Task Manager را نساز**.

خروجی باید دارای این قابلیت‌ها باشد: اتصال آسان مدل‌ها با Trait، انتخاب منبع در سطح هر برد، دریافت داده بهینه، اعمال قوانین سروری، Drawer عمومی و غنی، بخش‌های جزئیات اختیاری (مانند زیرتسک و وابستگی)، تجربه بصری باکیفیت Board/List و تست‌های واقعی. هر بخش باید بدون نصب Calendar یا Task Manager کار کند.

### واقعیت‌های مشاهده‌شده در ZIP و الزام حفظ آن‌ها

- `src/Support/BoardBuilder.php` با `provider()`, `handler()`, `settings()`, `cardView()`, `columnView()`, `listView()`, `build()` موجود است.
- `src/Contracts/DataProvider.php`, `src/Contracts/ActionHandler.php`, `src/Data/{BoardContext,BoardQuery,CardData,ActionCommand,ActionResult,PageResult}.php` موجودند.
- `src/Support/{BoardRegistry,ContextFactory,AuthorizationGuard,IdempotencyGuard}.php` و بخش‌های انتقال، شمارش، مرتب‌سازی، Bulk و Realtime وجود دارند.
- `src/Livewire/Concerns/HandlesCardDetails.php` فعلاً `provider()->card(...)` را خوانده و در `$detail` قرار می‌دهد.
- `resources/views/components/card-details-drawer.blade.php` فعلاً عنوان، badge، شرح، پیوست و مسئولان را نمایش می‌دهد؛ `card-details-modal.blade.php` نیز موجود است.
- `resources/views/components/{card,stage,list-row,toolbar,board}.blade.php` و `resources/css/kanban.css` نقطه‌های توسعه UI هستند.
- در ZIP بررسی‌شده Trait `HasKanbanCards` یا Provider اختصاصی Eloquent دیده نشد؛ در مخزن اجرایی قبل از نوشتن، وجود نسخه جدید را دوباره بررسی کن.
- نمونه‌های تست `tests/Scenarios/KB...` موجودند؛ **تست‌های قبلی را حذف یا با assertion صوری سبز نکن**.

## ۱. اصول معماری غیرقابل مذاکره

1. Kanban **کامپوننت نمایش و تعامل** است و مالک دیتای Task/Order/Ticket/CRM، کامنت، چک‌لیست یا پیوست نیست.
2. هسته نباید Migration، جدول، `branch_id`، `tenant_id`، `user_id`، مدل Eloquent، Filament، Mary UI، Calendar یا Task Manager اجباری داشته باشد.
3. اتصال Eloquent از طریق Trait و Provider **اختیاری** است. مسیر `BoardFactory + DataProvider + ActionHandler` برای مصرف‌کنندگان فعلی حفظ شود.
4. افزودن Trait به مدل به‌معنای نمایش عمومی آن در هر برد نیست. مدل فقط با **ثبت سروری صریح** و **مجازشدن برای برد مشخص** قابل استفاده شود.
5. بررسی دسترسی خواندن و نوشتن باید در سمت سرور و در هر درخواست انجام شود؛ نمایش ندادن دکمه یا فیلترکردن در مرورگر امنیت نیست.
6. اگر یک برد فقط منبع `tickets` را مجاز کرده باشد، حتی با شناسه جعلی از `orders` نباید بتوان جزئیات دید یا عملیاتی اجرا کرد.
7. تعریف منبع و مجوز در زمان درخواست از Container قابل بازسازی باشد؛ Closure و مدل Eloquent در وضعیت سریال‌شده Livewire ذخیره نشود.
8. در عملیات نامطمئن شبکه، نتیجه «unknown» را موفق اعلام نکن. Idempotency (جلوگیری از اجرای تکراری) و کنترل نسخه/تعارض باید حفظ شوند.
9. از شکستن API عمومی پرهیز کن. تغییر ناسازگار فقط با مستند مهاجرت و تست سازگاری معتبر است.
10. به‌جای پیاده‌سازی دوباره بخشی که از قبل موجود است، آن را گسترش بده. اول تست موجود را اجرا و baseline ثبت کن.

## ۲. قرارداد اتصال سریع مدل‌ها — Trait و قوانین مدل

### ۲.۱ توسعه‌دهنده با کمترین تنظیم بتواند شروع کند

- Trait پیشنهادی: `Karnoweb\Kanban\Concerns\HasKanbanCards`.
- یک متد مرکزی قابل بازنویسی روی مدل: `kanbanDefinition()` که یک تعریف تایپ‌شده از نگاشت‌ها، قابلیت‌ها و سیاست‌ها برگرداند.
- مقادیر پیش‌فرض کاربردی: `id`, `title`, فیلد وضعیت قابل انتخاب، توضیح، اولویت، مسئول، برچسب، تاریخ، نمای کارت، عملیات.
- امکان نگاشت ستون‌های متفاوت: مثلاً `Task.status`, `Order.fulfillment_status`, `Ticket.state`.
- تعریف مراحل می‌تواند از Enum (نوع شمارشی PHP)، فهرست ثابت یا قرارداد سفارشی بیاید.
- تعریف باید بتواند source key، نگاشت stage، وضعیت مجاز، permission policy، form handler، card badges، filters، sorting، aggregates و sections مربوط به Drawer را معرفی کند.
- اجازه بده مدل ساده با Trait + یک متد + ثبت منبع + تعریف برد کار کند؛ برای قوانین پیچیده سرویس/Handler سفارشی معرفی شود.
- اشتراک Trait بین مدل‌ها نباید باعث اشتراک وضعیت یا Scope شود.

### ۲.۲ ثبت و انتخاب منابع در سه سطح

- **منابع ثبت‌شده:** مثل `tasks`, `tickets`, `orders`, `opportunities` در Service Provider میزبان، با کلید ثابت و کلاس معتبر.
- **منابع مجاز یک برد:** مثلاً `support.board` فقط tickets؛ `sales.board` فقط opportunities؛ `operations.board` orders + tickets.
- **فیلترهای فعال کاربر:** تنها زیرمجموعه منابع مجاز همان برد، نه وسیله افزایش دسترسی.

قواعد:

- عدم ثبت مدل = عدم استفاده؛ اسکن همه مدل‌ها یا اجرای query هنگام startup ممنوع.
- رجیستری باید کلید تکراری/نامعتبر/کلاس فاقد قرارداد را رد کند.
- لیست منابع هر برد را سرور تعیین کند؛ دستکاری property Livewire، query string یا درخواست API نباید اجازه اضافه‌کردن منبع بدهد.
- `[]` نباید به شکل خطرناک «همه منابع» تفسیر شود؛ معنای آن را به‌صورت امن تثبیت و مستند کن.
- برای برد مختلط، کلید کارت باید از source + شناسه اصلی تشکیل شود و بدون collision باشد؛ `tasks:12` و `tickets:12` دو رکورد مستقل‌اند.
- مقادیر stage متفاوت منابع تنها از طریق `stageMap` صریح به یک ستون مشترک وصل شوند.
- مسیرهای `counts`, search, card details, archives, bulk, move, update و realtime` همگی از همان allowlist سروری پیروی کنند.

### ۲.۳ Provider خودکار و عملیات دامنه

- یک Eloquent DataProvider اختیاری ایجاد کن که قرارداد فعلی `DataProvider` را رعایت کند.
- عملیات نوشتن را فقط از Handler معتبر مدل/میزبان عبور بده. تغییر وضعیت Order و Ticket باید از سرویس مالک دامنه انجام شود؛ `update(['status'=>...])` بدون بررسی قواعد تجاری ممنوع.
- قابلیت‌های هر کارت مانند `canView`, `canEdit`, `canMove`, `canDelete`, `canComment` مستقل تعریف شوند و در سرور دوباره بررسی شوند.
- در نبود مجوز صریح، برای عملیات حساس **deny by default** رعایت شود.
- رویداد موفق پس از commit و فقط یک‌بار منتشر شود؛ listener نباید باعث ذخیره دوباره تغییر شود.

## ۳. کارایی واقعی برای بردهای بزرگ

1. بارگذاری کارت‌های هر ستون در DB فیلتر شود، نه پس از `Model::all()` یا دریافت کل برد.
2. Scope مالکیت/سازمان/مستأجر و source در خود query اعمال شود؛ فیلتر فقط در PHP برای حذف رکورد غیرمجاز قابل قبول نیست.
3. صفحه‌بندی هر ستون مستقل از دیگری باشد؛ cursor معتبر به scope، board، stage، filter، sort و source وابسته باشد.
4. جست‌وجو و sort فقط روی فیلدهای allowlist‌شده اجرا شوند؛ SQL injection و sort از فیلد دلخواه رد شود.
5. روابط لازم تنها برای کارت‌های صفحه جاری eager load شوند؛ N+1 را با query count تست کن.
6. شمارش کل ستون مستقل از Loaded Count باشد؛ metrics سفارشی فقط از query تجمیعی مجاز ارائه شوند.
7. جابه‌جایی و مرتب‌سازی از anchor (شناسه قبل/بعد) استفاده کنند و در حالت معمول به بازنویسی تمام کارت‌های ستون منجر نشوند؛ روش نگهداری ترتیب به میزبان تحمیل نشود.
8. WIP (حد ظرفیت کار در جریان) در سرور، در حضور انتقال هم‌زمان و در تراکنش مناسب رعایت شود.
9. اگر رویداد Realtime می‌رسد، فقط بردها/منابع/Scope مرتبط تازه‌سازی شوند و رویداد تکراری وضعیت را دوبار تغییر ندهد.
10. برای حجمی مانند ۱۰ ستون × ۱۰هزار کارت در کل، تعداد مدل‌های materialize شده در نمایش اولیه باید محدود و قابل گزارش باشد؛ معیارهای عددی دقیق را پس از baseline در CI قفل کن.

## ۴. اولویت محصولی این مرحله: Drawer عمومی و واقعاً کاربردی

### ۴.۱ Drawer را از صفر و موازی نساز

از این نقاط موجود آغاز کن:

- `src/Livewire/Concerns/HandlesCardDetails.php`
- `resources/views/components/card-details-drawer.blade.php`
- `resources/views/components/card-details-modal.blade.php`
- `resources/views/components/card-attachments.blade.php`
- `resources/views/components/card-assignees.blade.php`
- `src/Support/ViewResolver.php` و `BoardBuilder`.

`openDetails()` باید همچنان کار کند. جزئیات پایه کارت با مسیر فعلی نمایش داده شود، اما بخش‌های افزوده از یک قرارداد **اختیاری** و مجوزمند خوانده شوند. افزودن متد اجباری به اینترفیس عمومی DataProvider برای همه مصرف‌کنندگان قبلی راهکار مطلوب نیست؛ اگر لازم شد قرارداد افزونه‌ای جدا تعریف کن.

### ۴.۲ قرارداد بخش‌های Drawer

پیشنهاد اسامی (اگر ساختار مخزن نام مناسب دیگری دارد، یک نام نهایی انتخاب و مستند کن):

- `CardDetailsProvider` برای اطلاعات تکمیلی کارت.
- `CardDetailSectionData` شامل key، title، order، state، summary، optional pagination و capabilities.
- `CardDetailAction` برای عملیات امن هر بخش و نتیجه استاندارد.
- Registry سروری بخش‌ها یا روش ثبت در `kanbanDefinition()` / `BoardBuilder`.

فهرست بخش‌های آماده UI (بدون دیتابیس/منطق تجاری داخلی):

| بخش | رفتار پیش‌فرض |
|---|---|
| Summary / Properties | عنوان، شناسه، وضعیت، اولویت، منبع، زمان‌ها، افراد و فیلدهای اختصاصی |
| Description | متن امن، نمایش طولانی، ویرایش تنها در صورت handler و مجوز |
| Subtasks | فهرست فرزندان، پیشرفت، وضعیت، افزودن/تغییر وضعیت فقط اگر Provider پشتیبانی کند |
| Dependencies | «وابسته به» و «مسدودکننده»، نمایش شناسه/عنوان/وضعیت، جلوگیری از عملیات بدون Handler |
| Checklist | چند فهرست و آیتم، شمارش و درصد تکمیل، عملیات اختیاری |
| Comments / Activity | نظرها و تاریخچه با صفحه‌بندی و جداسازی دسترسی |
| Attachments | فهرست فایل‌های مجاز، thumbnail و لینک امن، بدون ذخیره‌ساز اجباری |
| Related Records | لینک‌های مجاز به Order/Ticket/CRM/Task، فقط داده مجاز همان Scope |
| Custom Sections | Blade/کامپوننت یا Presenter سفارشی با escape و قرارداد مشخص |

**حکم مهم:** Subtasks، Dependency، Comments، Checklist، Attachment و Activity در این مرحله فقط رابط آماده و قرارداد قابل وصل‌شدن دارند. مدل‌ها/جداول تسک، موتور وابستگی یا چک‌لیست متعلق به Task Manager **الان نباید ساخته شوند**. اگر Provider بخش داده یا قابلیت نداد، بخش کاملاً مخفی یا خواندنی باشد؛ داده جعلی نساز.

### ۴.۳ رفتار دقیق Drawer

- روی کارت Board و ردیف List یکسان باز شود؛ بر اساس board key + source + card ID و Scope سروری.
- عنوان، status، priority، assignee، تاریخ، actions و summary در سربرگ خوانا و ثابت نمایش داده شوند.
- عرض قابل تنظیم (پیشنهاد پیش‌فرض ۵۲۰–۶۰۰ px)، با RTL/LTR و حالت تمام‌صفحه موبایل.
- Backdrop، بستن با Escape، مدیریت فوکوس/برگشت فوکوس، focus trap، `aria` و جلوگیری از اسکرول ناخواسته پشت Drawer.
- اسکرول محتوای Drawer مستقل از Board؛ هدر و نوار اقدام در صورت نیاز ثابت بمانند.
- Lazy loading بخش‌های حجیم فقط بعد از بازشدن همان بخش؛ از لود همه comments/attachments هنگام باز کردن کارت خودداری کن.
- اطلاعات هر بخش با مجوز خاص خودش بخوان/ویرایش شود؛ صرف `canViewCard` مجوز مشاهده همه کامنت‌ها و پیوست‌ها نیست.
- اقدام‌های create/update/delete/reorder با نتیجه Success/Validation/Forbidden/Conflict/Unknown و پیام مناسب کار کنند.
- پس از ذخیره، فقط قسمت‌های لازم تازه‌سازی شوند؛ Realtime و cache با scope درست invalid شوند.
- فیلدهای تغییرکرده ذخیره‌نشده هنگام خروج هشدار مناسب داشته باشند؛ cancel بدون تغییر دامنه باشد.
- منوی «بازکردن در برنامه میزبان» یک لینک امن اختیاری باشد؛ نبود لینک مانع مشاهده جزئیات در پکیج نشود.
- URLها allowlist/sanitize شوند، HTML خام متن/کامنت escape شود؛ هیچ Blade/HTML دلخواه برگشتی از داده کاربر به عنوان کد اجرا نشود.
- اگر کارت هم‌زمان حذف شد یا مجوزش تغییر کرد، Drawer خطای مناسب نشان دهد و اطلاعات قبلی نشت نکند.

### ۴.۴ رفتار استفاده مستقل

- `Task` می‌تواند تمام بخش‌ها را ارائه دهد، اما Kanban آن‌ها را ذخیره نکند.
- `Order` ممکن است فقط Properties + Items + Fulfillment + Activity را ارائه دهد.
- `Ticket` ممکن است Comments + Attachments + SLA + Activity را ارائه دهد.
- یک Provider قدیمی که فقط CardData برمی‌گرداند باید همچنان Drawer پایه و قابل استفاده داشته باشد.
- کاربرد همه بخش‌ها با روشن/خاموش‌کردن تنظیمات و مجوز در سطح برد/مدل قابل کنترل باشد.

## ۵. UI/UX برد، لیست و جزئیات

- تصاویر مرجع Trello/Jira و طرح تأییدشده Kanban جهت **کیفیت طراحی و الگوهای تعامل** هستند؛ pixel-copy یا hardcode نمونه‌ها نکن.
- از اصلاحات قبلی کارت و Layout محافظت کن؛ سه سطح Workspace/Stage/Card بصری مجزا باشند.
- کارت: شناسه و عنوان در رأس، badgeهای محدود، شرح کوتاه، footer گروه‌بندی‌شده برای metadata؛ حالت compact/comfortable قابل تنظیم.
- Drawer باید نمایش کامل اطلاعات را بر عهده بگیرد، نه اینکه کارت پر از لیست پیوست‌ها و کامنت‌ها شود.
- List باید نمای منظم ستونی باشد، نه کارت Board کشیده‌شده در عرض صفحه؛ بازکردن Drawer در آن هم همان تجربه را بدهد.
- RTL/LTR، تم Light/Dark، موبایل، keyboard و reduced-motion را با آزمون مرورگر پوشش بده.
- استایل‌ها فقط داخل scope پکیج اثر کنند؛ فونت میزبان به ارث برسد؛ وابستگی جدید به Filament/Tailwind configuration میزبان تحمیل نکن.

## ۶. هماهنگی آینده با Calendar و Task Manager — بدون وابستگی

- یک مدل واحد می‌تواند در Kanban وضعیتش تغییر کند و در Calendar موعدش نمایش داده شود؛ اطلاعات تکراری ذخیره نکن.
- رویداد تغییر دامنه متعلق به Handler میزبان است. پس از تغییر موفق، میزبان می‌تواند رویداد خودش را منتشر کند؛ Kanban بدون دانستن Calendar بتواند refresh شود.
- قرارداد شناسه/نسخه/منبع تغییر را مستند کن تا بعدها Adapter جداگانه بتواند اتصال فراهم کند؛ API مستقیم به Calendar یا Task Manager اضافه نکن.
- نام کلاس یا Trait متعلق به Calendar یا Task Manager نباید در require/boot هسته Kanban وارد شود.

| K3 | Drawer عمومی و Sectionها | ۹ نوع بخش عمومی، fallback، lazy load، مجوزهای بخشی |
| K4 | هماهنگی Board/List و رابط حرفه‌ای | UI واکنش‌گرا، Drawer عملیاتی، RTL/Dark، A11y |
| K5 | تست جامع، سه نمونه مستقل، مستندات و release gate | تمامی تست‌ها و سناریوها سبز، بدون TODO اجباری |

فازها ترتیب توسعه‌اند، نه نسخه انتشار مستقل. پس از K5 خروجی ZIP نهایی برای بازبینی کارفرما تهیه کن.

## ۸. سناریوهای پذیرش الزامی (هر سناریو: تست PHP و در صورت UI تست مرورگر)

**ثبت منابع و دسترسی**

1. مدل Task با Trait، تعریف حداقلی و ثبت صریح کار کند.
2. مدل Order با نام فیلد وضعیت متفاوت و قوانین خاص، بدون تغییر هسته کار کند.
3. مدل Ticket با شناسه عددی برابر Task در یک برد مختلط collision نداشته باشد.
4. برد فقط Tickets هیچ query روی Orders نکند.
5. تلاش برای گرفتن details کارت Orders از برد Tickets با درخواست جعلی رد شود.
6. تلاش برای move/bulk/archive کارت منبع غیرمجاز در سرور رد شود.
7. scope کاربر A هیچ مدل خصوصی کاربر B را در list, count, search یا details برنگرداند.
8. برد عمومی فقط با مجوز صریح قابل خواندن ناشناس باشد.
9. disabled feature با فراخوانی مستقیم متد Livewire قابل اجرا نباشد.
10. Provider/Handler قدیمی بدون Trait همچنان کار کند.

**کارایی و عملیات**

11. برد ۱۰ ستونی با حجم زیاد فقط صفحه اولیه را query و hydrate کند.
12. load-more هر ستون ترتیب stable و بدون کارت تکراری داشته باشد.
13. تغییر فیلتر cursor قبلی را امن باطل کند.
14. سرجمع ستون از Loaded Count مستقل باشد.
15. نقل مکان هم‌زمان به آخرین ظرفیت WIP فقط یک درخواست موفق داشته باشد.
16. update پس از نسخه قدیمی خطای conflict قابل بازیابی داشته باشد.
17. operation-id تکراری عملیات دامنه را دوباره اجرا نکند.
18. پس از خطای نامشخص عملیات، نمایش «موفق» جعلی رخ ندهد.
19. ۱۰۰ کارت با ارتباط assignee/labels در یک صفحه باعث N+1 غیرقابل‌قبول نشود.
20. انتقال کارت به منبع/ستون غیرقابل نگاشت رد شود.

**Drawer و بخش‌های اختیاری**

21. Provider ساده با فقط `CardData` یک Drawer پایه سالم بدهد.
22. Task دارای جزئیات کامل و هشت بخش افزونه‌ای به‌درستی نمایش داده شود.
23. Order دارای Properties + Items + Activity بدون نمایش Subtasks کار کند.
24. Ticket دارای Comments + Attachments با مجوز مستقل بخش‌ها کار کند.
25. بخش غیرفعال داده یا عملیات اضافی نخواند.
26. lazy load بخش Activity فقط هنگام بازشدن همان بخش اجرا شود.
27. pagination نظرها و پیوست‌ها تعداد محدودی رکورد برگرداند.
28. تغییر یک فیلد با validation error داده غلط ذخیره نکند و خطا کنار فیلد بماند.
29. لغو فرم بدون ذخیره، مدل اصلی را تغییر ندهد.
30. کش شدن مجوز قبلی باعث نمایش داده پس از revocation نشود.
31. کارت حذف‌شده هنگام باز بودن Drawer بدون نمایش داده محرمانه واکنش نشان دهد.
32. HTML مخرب و `javascript:` در عنوان، توضیح و لینک هرگز اجرا نشوند.
33. Drawer در Board و List یک رفتار و یک منبع حقیقت داشته باشد.
34. Drawer با Escape و صفحه‌کلید مدیریت فوکوس درست داشته باشد.
35. Drawer در موبایل قابل اسکرول، بدون overflow ناخواسته و قابل بستن باشد.
36. Realtime به‌روزرسانی کارت دیگر برد/مستأجر را در این Drawer نشان ندهد.

**سازگاری و یکپارچگی آزاد**

37. Kanban بدون نصب Calendar یا Task Manager نصب و رندر شود.
38. ثبت Adapter اختیاری برای یک مدل CRM باعث نیاز اجباری دیگر مدل‌ها نشود.
39. روی همان صفحه دو Board با sources متفاوت cache/URL/selection مستقل داشته باشند.
40. تم Light/Dark و RTL/LTR در Board/List/Drawer در تست مرورگر بررسی شوند.
41. اختلاف داده بعد از commit با refresh صحیح UI حل شود؛ نه با اجرای مجدد دستور نوشتن.
42. همه تست‌های قدیمی مخزن نیز موفق باقی بمانند.

برای هر سناریو تست قابل تکرار در `tests/` و در صورت وجود سنت مخزن فایل توضیح Markdown ایجاد یا به‌روزرسانی کن. از assertion صوری، skip بدون علت یا تستی که handler را bypass کند استفاده نکن.

## ۹. مستندات و خروجی لازم

مستندات مصرف‌کننده واقعی تهیه کن، حداقل:

- `docs/USAGE.md`: نصب، ثبت برد، Trait حداقلی، Provider سفارشی، اتصال Blade/Livewire.
- `docs/CONFIGURATION.md`: تمام configها، مقادیر پیش‌فرض، امنیت، appearance، load limits.
- `docs/SOURCES.md`: رجیستری، sources هر برد، مثال سه برد با منابع متفاوت.
- `docs/DRAWER.md`: بخش‌های پایه و افزونه، اولویت، مجوزهای بخشی، Actionها و fallback.
- `docs/EXAMPLES-CRM-ORDERS-TICKETS.md`: سه مثال کامل با مدل میزبان فرضی، بدون افزودن آنها به core.
- `docs/UPGRADE.md`: نگاشت API قبلی به API جدید و تغییرات احتمالی.
- `docs/TEST-SCENARIOS.md`: ورودی، خروجی مورد انتظار و روش اجرای تست.

در گزارش انتهایی حتماً بده: فایل‌های تغییرکرده، APIهای جدید و تغییرکرده، تست‌های واقعی با شمارش، query count نمونه، لایه امنیتی، تصاویر Board/List/Drawer در Light/Dark/RTL/Mobile و مشکلات باقی‌مانده. اگر تست مرورگر/Composer قابل اجرا نیست، **صادقانه اعلام کن و تأیید Production صادر نکن**.

## ۱۰. توقف و تحویل

**پس از این مرحله Task Manager را پیاده‌سازی نکن و Calendar را تغییر نده.** خروجی این مرحله: ZIP جدید Kanban به همراه مستندات و نتایج تست برای بازبینی. شروع مرحله بعد (Calendar) مستقل و پس از ارزیابی این خروجی امکان‌پذیر است.
