# CRM, Orders, and Tickets examples

These examples describe host-owned Eloquent models. They are not migrations or models shipped by the Kanban core. Each host model uses `HasKanbanCards`, declares its own status mapping and visibility scope, and is registered under a fixed source key.

## CRM opportunities

Register `opportunities` and allow only that source on `sales.pipeline`. Map the host's `stage` enum to the board's pipeline stages. The model's `visibleQuery()` scopes opportunities by the current organization; `authorize()` checks view and edit permissions. A move hook calls the CRM transition service so forecast and audit rules run. Do not use a generic status update for domain transitions.

## Orders

Register `orders` and allow only that source on `fulfillment.orders`. Map `fulfillment_status` values such as `pending`, `packing`, and `shipped` to board stages. The model can expose `total` as a scalar metric and a custom card presenter can show customer and order number. Disable arbitrary card deletion if order retention rules forbid it. A custom handler calls the order service and returns a typed `ActionResult`.

## Support tickets

Register `tickets` and allow only that source on `support.tickets`. Map the host's `state` field and scope queries by organization and agent assignment. Use a `TicketDetails` `CardDetailsProvider` for SLA, paged comments, attachments, and activity. Each section checks its own policy; `canViewCard` alone does not grant comment or file access. Attachment URLs should be generated by the host's authorized download route.

## Mixed operations board

A separate board may allow both `orders` and `tickets`, but must provide a complete `stageMap` for both models. Its source filter can narrow that fixed list; it cannot add CRM opportunities or another registered source. Manual ordering across sources is disabled unless a host supplies a shared `RankStrategy`.

For concrete model syntax and registration examples, see [Trait and Eloquent guide](21-trait-eloquent-guide.md), [multi-source boards](22-multi-source-boards.md).

**Step-by-step implementation (Persian, with final workbench code):** [examples/README.md](examples/README.md) — [CRM](examples/crm.md), [Tasks](examples/task-manager.md), [Tickets](examples/ticketing.md), [Orders](examples/orders-approvals.md).

## Complete host-side adapter skeleton

The following host models assume existing tables and an organization ID supplied by the trusted `ScopeResolver`. They add no package schema. The example grants organization members read access and delegates each write ability to the host's registered Laravel policies. If read permissions vary within an organization, add those constraints to `visibleQuery()` as well.

```php
namespace App\Models;

use Illuminate\Database\Eloquent\{Builder, Model};
use Illuminate\Support\Facades\Gate;
use Karnoweb\Kanban\Concerns\HasKanbanCards;
use Karnoweb\Kanban\Data\BoardContext;
use Karnoweb\Kanban\Models\KanbanModelDefinition;

abstract class OrganizationKanbanModel extends Model
{
    use HasKanbanCards;

    public static function kanbanDefinition(): KanbanModelDefinition
    {
        return KanbanModelDefinition::make(static::SOURCE, static::class)
            ->fields(['title' => static::TITLE, 'stage' => static::STATUS, 'version' => 'version'])
            ->stages(static::STAGES)
            ->visibleQuery(fn (Builder $query, BoardContext $context) =>
                $query->where('organization_id', $context->scopeKey))
            ->authorize(fn (string $ability, ?Model $record, BoardContext $context): bool =>
                $record !== null && (string) $record->organization_id === $context->scopeKey
                && ($ability === 'view' || Gate::allows($ability, $record)))
            ->sorts(['title'])
            ->searchable([static::TITLE]);
    }
}

final class Opportunity extends OrganizationKanbanModel
{
    protected const SOURCE = 'opportunities';
    protected const TITLE = 'name';
    protected const STATUS = 'stage';
    protected const STAGES = ['new' => 'New', 'negotiating' => 'Negotiating', 'won' => 'Won'];
}

final class Order extends OrganizationKanbanModel
{
    protected const SOURCE = 'orders';
    protected const TITLE = 'order_number';
    protected const STATUS = 'fulfillment_status';
    protected const STAGES = ['pending' => 'Pending', 'packing' => 'Packing', 'shipped' => 'Shipped'];
}

final class Ticket extends OrganizationKanbanModel
{
    protected const SOURCE = 'tickets';
    protected const TITLE = 'subject';
    protected const STATUS = 'state';
    protected const STAGES = ['new' => 'New', 'answering' => 'Answering', 'resolved' => 'Resolved'];
}
```

Register all model sources explicitly in the host service provider. Registration alone exposes none of them on a board.

```php
$models = app(\Karnoweb\Kanban\Models\KanbanModelRegistry::class);
$models->register('opportunities', \App\Models\Opportunity::class);
$models->register('orders', \App\Models\Order::class);
$models->register('tickets', \App\Models\Ticket::class);
$boards = app(\Karnoweb\Kanban\Support\BoardRegistry::class);
foreach (['sales.pipeline', 'fulfillment.orders', 'support.tickets'] as $key) {
    $boards->register($key, \App\Kanban\ResourceBoardFactory::class);
}
```

The factory chooses its allowlist from the server board key. A client-supplied source cannot change it.

```php
namespace App\Kanban;

use Karnoweb\Kanban\Contracts\{ActionHandler, BoardFactory};
use Karnoweb\Kanban\Data\{ActionCommand, ActionResult, BoardContext, BoardData, BoardDefinition};
use Karnoweb\Kanban\Support\BoardBuilder;

final class ResourceBoardFactory implements BoardFactory
{
    public function make(BoardContext $context): BoardDefinition
    {
        [$source, $title] = match ($context->boardKey) {
            'sales.pipeline' => ['opportunities', 'CRM pipeline'],
            'fulfillment.orders' => ['orders', 'Fulfillment'],
            'support.tickets' => ['tickets', 'Support tickets'],
        };

        return (new BoardBuilder)->key($context->boardKey)
            ->board(new BoardData($context->boardKey, $title, $context->scopeKey))
            ->sources([$source])->handler(ResourceActionHandler::class)
            ->settings(['features' => ['create_card' => false], 'views' => ['detail_surface' => 'drawer']])
            ->build();
    }
}

final class ResourceActionHandler implements ActionHandler
{
    public function execute(ActionCommand $command, BoardContext $context): ActionResult
    {
        $service = match ($context->boardKey) {
            'sales.pipeline' => \App\Services\CrmTransitions::class,
            'fulfillment.orders' => \App\Services\OrderFulfillment::class,
            'support.tickets' => \App\Services\TicketWorkflow::class,
        };

        return app($service)->executeKanban($command, $context);
    }
}
```

Each existing domain service implements `executeKanban(ActionCommand, BoardContext): ActionResult`: it resolves the source-qualified ID within the actor's scope, checks the expected version and transition policy, records the operation ID, commits once, then emits its domain event. Its implementation belongs to the host. The adapter never calls a direct status update on an Order or Ticket.

For richer details, add `detailsProvider(HostDetailsProvider::class)` to the relevant branch of this factory. The [Drawer contract](DRAWER.md) allows Order Items/Activity, Ticket Comments/Attachments, or CRM Related Records without requiring those sections on any other source.
